---
title: Конфигурация и состояние
description: Общее состояние, переопределения и сгенерированные файлы выполнения.
---
Обычный пользователь root — `$XDG_CONFIG_HOME/argvus` (обычно `~/.config/argvus`). Управляемые логические настройки хранятся в `config.json`. Там канонически задаются темы, акценты, обои, интервалы и границы; dot-файлы остаются производными проекциями для совместимости для текущих потребителей Hyprland Lua и оболочки, пока эти потребители переходят на `data/`.

`argvus-config` — это единственный писатель ниже `generated/`. Каждый потребительский файл, принадлежащий ARGVUS, является проекцией `config.json`, включая Hyprland, GTK, Qt6ct, Waybar, Quickshell, Dunst, Hyprlock, панель задач Waybar и профили виджетов-телеметрии, деревья конфигураций Yazi и Superfile, деревья профилей терминала и Qt, управляемые блоки шрифтов и таблицу стилей съемных устройств. Компоненты разрешают явные пользовательские переопределения, затем сгенерированный вывод, затем значения по умолчанию пакета. Rofi не является проекцией: `argvus-launcher` владеет его файлами, а пользовательские копии живут под `data/rofi/`. Обычная проекция темы/перезагрузка никогда не продвигает ни сгенерированные, ни упакованные файлы в пользовательское переопределение. Документация и инструменты должны идентифицировать логический источник вместо того, чтобы просить пользователей редактировать сгенерированный вывод.

`argvus-appearance`, таким образом, отвечает за оркестровку тем и акцентов, в то время как `argvus-config` отвечает за каноническое состояние и структурированную проекцию. `argvus theme-switch` (транзакция `argvus config theme-apply`) и `argvus config accent` проверяют, блокируют и фиксируют через `argvus-config`, когда это возможно, а затем согласуют потребителей совместимости, которые не могут напрямую читать `config.json`. Эти адаптеры включают нативный файл Qt6ct, подсказки GTK `settings.ini` и `gsettings`, терминальные и системные мониторы, foot, собственный каталог конфигурации superfile и приветственный экран перед аутентификацией. Вспомогательная программа, которой нужен новый адаптер, должна добавлять его туда, никогда не внутри `generated/`.

Владение временем выполнения намеренно разделено по ответственности: Rust управляет каноническим хранилищем, проверкой схем, миграциями, моделью путей, блокировками, атомарными записями, хэшами проекций и структурированными рендерерами. Shell остаётся только в виде небольших точек входа для совместимости или адаптеров для внешних потребителей, таких как `hyprctl`, и скриптов тем, принадлежащих активам. Python зарезервирован для тестов, аудитов и вспомогательных инструментов разработки; он не является частью критически важного настольного времени выполнения.

`argvus config apply` является границей перестройки (`project` остаётся совместимым написанием). Он регенерирует отсутствующие выходные данные, даже если канонический документ не изменился, рендерит проекторы на стадии подготовки и атомарно заменяет дерево `data/` только после того, как каждая проекция успешно выполнена. Жизненный цикл сессии остаётся под управлением `argvus sessionctl`, который использует этот манифест для планирования целевых перезагрузок.

Когда вызывающий уже зафиксировал генерацию — `apply-theme`, изменение акцента, `set`/`patch` или изменение блока виджета-телеметрии — `reload` **применяет** эту генерацию вместо того, чтобы проецировать её снова. Он считывает план из манифеста, восстанавливает целевых потребителей и проецирует только тогда, когда манифест отсутствует или в нём нет ожидающей работы. Повторная проекция в этот момент создала бы идентичное дерево и отбросила бы план, который только что была произведена мутацией.

Манифест также фиксирует операционную генерацию, хэш эффективной конфигурации, изменённые домены и список сгенерированных файлов. `data/internal/generation.json` — это одноразовый локальный маркер проекции и никогда не является пользовательским предпочтением. `argvus config status` сравнивает эти записи с разрешённой конфигурацией и сообщает о отсутствующих или лишних сгенерированных файлах.

Мутации следуют тем же границам движка: `UserConfig` клонируется в `NextUserConfig`, проверяется, разрешается в `EffectiveConfig`, проецируется, и только затем сохраняется. `.config-transaction.json` — это состояние оперативного восстановления; `argvus config recover` детерминированно повторно проецирует предыдущий канонический документ после сбоя между публикацией `data/` и `config.json`. Перезагрузка запрашивается только после фиксации, и сбой перезагрузки не откатывает согласованную сохранённую конфигурацию.

## Модель разрешения

```text
config.json logical model
    ↓
ARGVUS native compatibility state and per-app override
    ↓
ARGVUS generated runtime file
    ↓
/usr/share/argvus packaged default
    ↓
upstream default
```
Точные кандидаты различаются в зависимости от компонента, но принцип остаётся неизменным: пользовательское переопределение имеет приоритет, сгенерированный вывод является производным состоянием, а пакеты файлов остаются только для чтения. Сессия экспортирует `ARGVUS_CONFIG_HOME` и `ARGVUS_SYSTEM_CONFIG`, чтобы вспомогательные службы и пользовательские сервисы разрешали одни и те же корневые элементы.

Восстановление при перезагрузке следует `recover → ensure → migrate → apply → runtime reload`, и этап проекции пропускается, если входящий манифест уже описывает зафиксированное поколение. `ensure` материализует `config.json` из стандартных значений схемы только при отсутствии профиля и заполняет отсутствующие поля без замены явных `false`, `0` или пользовательских значений. Существующий повреждённый документ остаётся ошибкой, а не заменяется без уведомления.

Постоянные мутации сравнивают разрешённые старые и новые конфигурации через `ChangedDomains`. После фиксации (commit) один запрос на перезагрузку отправляется через `argvus sessionctl`; ошибка перезагрузки регистрируется и фиксируется без отката зафиксированной конфигурации. Запуск сеанса выполняет восстановление перед материализацией и проекцией bootstrap, поэтому потребители не запускаются в рамках оставшейся транзакции.

| Состояние | Назначение |
| --- | --- |
| `config.json` | Канонические управляемые логические настройки; единственный источник для всего ниже `generated/`. |
| `.active-theme`, `.accent-color`, `.accent-custom` | Входные данные для миграции наследия; не являются источниками во время выполнения и не генерируются заново. |
| `.wallpaper-custom` | Входные данные для миграции наследия для `appearance.wallpaper`; не является источником во время выполнения. |
| `.spaces`, `.borders` | Входные данные для миграции макета наследия; канонические значения хранятся под `layout` в `config.json`. |
| `fonts.conf` | Проекция совместимости канонических выборов шрифтов. |
| `generated/effects` | Проекция совместимости канонических эффектов; одноразовая. |
| `$XDG_STATE_HOME/argvus/config-projection.json` | Манифест проекции: изменённые секции, затронутые потребители и требуется ли перезагрузка. Читается `reload`; никогда не является источником истины. |
| `$XDG_STATE_HOME/argvus/widget-telemetry-blocks` | Настройки блока устаревшей телеметрии. Читается только как резервный вариант при миграции; канонические значения находятся в `/control_panel/widget_telemetry_blocks`, и файл больше не записывается. |

Свойство является каноническим, когда оно читается из `config.json` и проецируется оттуда. Свойство является производным, когда оно проецируется, но также может использоваться в качестве входных данных для миграции. Всё, что компонент продолжает записывать во время выполнения — кэш, нативный конфигурационный файл в `$XDG_CONFIG_HOME/<app>`, файл состояния приветствия — является целевым адаптером и не должно читаться обратно как конфигурация.

Проекция охватывает пользователей для Hyprland, GTK/Qt, Waybar, Quickshell, терминалов, уведомлений, экрана блокировки и нативных приложений. Hyprland считывает активные и неактивные цвета рамки из выбранной темы; явный `appearance.accent_custom=true` — единственный случай, который переопределяет активную/групповую рамку цветом акцента пользователя. Переключение темы повторно применяет эти значения через перезагрузку композитора, поэтому невозможно сохранить цвета предыдущей темы. Если пользовательская конфигурация создается заново, эффекты по умолчанию включают анимации. Удаление `generated/` и запуск `argvus config apply` воссоздает его побайтово из `config.json`; прямое редактирование сгенерированных файлов недолговечно. 
Диагностика во время выполнения должна идентифицировать полный набор выполнения: путь к бинарному файлу, версию/ревизию, корень ресурсов, корень конфигурации, корень данных, корень сгенерированных данных, внутренний корень и манифест проекции. `status --verbose` раскрывает этот набор и
сравнивает опубликованное поколение/хэш с текущей разрешённой конфигурацией. Разработческие и тесты установленных пакетов являются отдельными режимами; ни один из них не может тихо переключиться на несвязанный исполняемый файл или домашнюю папку разработчика. `apply` также является границей согласования для устаревших объединённых идентификаторов тем: значение вроде `argvus-dark-spaced` становится `theme=argvus-dark` и `variant=spaced` перед разрешением. Идентичность упакованного ресурса не записывается в манифест в этом выпуске, поэтому ни один диагностический файл её не описывает.
