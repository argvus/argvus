`argvus-greeter`はgreetdインターフェースを提供します。セッション読み込みスピナーは、`/usr/lib/argvus/greeter/handoff --wayland`というハンドオフヘルパーのWaylandモードであり、`argvus-session-loading.service`によって起動されます。GTKオーバーレイ`argvus loading-theme`は、テーマの切り替えや直接リロードをカバーします。`argvus-boot-splash`は、個別のブートスプラッシュを提供します。`argvus-lock`はHyprlockの設定を提供します。

テーマの状態は、グリーターとセッションの移行の間で引き継がれますが、これらのパッケージはライフサイクルやインストールされるペイロードが異なります。

グリータはユーザーの認証セッションの前に実行され、greetdのIPC/PAM境界を使用します。セッション読み込みオーバーレイは、新しいWaylandソケットが利用可能になると開始され、`argvus sessionctl ready`がデスクトップコンポーネントを起動すると終了するため、セッションの起動全体をカバーします。Plymouthテーマは起動パスに属しており、ログイン画面ではありません。ロックコンポーネントはログイン後に使用され、どちらのグリータも置き換えません。

ログインハンドオフには独自の DRM サーフェスがあります。認証が成功すると、グリーターはセッションを開始するよう greetd に依頼する前に `/usr/lib/argvus/greeter/handoff` (`argvus-greeter-handoff`) を起動します。ヘルパーは、グリーターのコンポジターが DRM マスターを解放するとすぐにそれを取得し、ユーザーコンポジターが引き継ぐまで画面にフレームを保持します。グリーターが終了した後も実行され続けます。greetd がセッションを受け入れるとすぐに、グリーターはそのコンポジターを終了します：greetd はグリーターセッションが終了した後にのみユーザーセッションを開始し、コンポジターは greetd の SIGTERM では終了しないため、これがないとログインは greetd の 5 秒間の終了を待つことになります。アクティブな Hyprland は終了するとすべての出力をオフにし、その後モニターは信号を失います。したがって、コンポジターを終了する前に、グリーターはシートを空の VT 12 に切り替えます（logind `Seat.SwitchTo`、polkit はアクティブセッションを許可します。VT 12 は autovt 範囲の上にあるため、そこで getty は起動しません）。それ `XDG_SEAT`（未設定時は`seat0`）からシートにアクセスし、`seat/self`としてはアクセスしません：Kittyはグリーターをその独自のsystemdスコープに移動させ、logindセッションの外に置きます。ここではlogindは呼び出し元のシートを解決できません。logindはグリーターセッションを非アクティブ化し、そのコンポジターからDRMマスターを取得しますが、コンポジターは最後のフレームを画面に表示したまま動作を続けます。ヘルパーがマスターを取得し、そのフレームをページフリップで置き換え、グリーターのカーソルを隠します。グリーターはこれを待ちます（ヘルパーは描画後にのみ`ping`に応答します）そしてその後にだけコンポジターを終了します。ヘルパーは`start-hyprland`ウォッチドッグ、すなわちグリーターセッションコマンドのみをSIGKILL（タイミングログ内の`greeter.watchdog-stop-requested`）で停止します：その後、greetdはすぐにユーザーセッションを開始し、停止されたウォッチドッグはHyprlandを再起動できません。非アクティブでDRMマスターを持たないコンポジターは後で終了を指示されます（`greeter.compositor-exit-deferred`）：独自のグループのプロセスが引き渡しサーフェスまで待機します ソケットを取り外し、最大で10秒、その後さらに3秒経過し、`argvus config hyprland exit`を実行します。コンポジターの終了処理はそのデバイスをlogindに戻し、NVIDIAドライバ上ではlogindはその後約0.5秒かけてDRMクライアントを閉じ、他には何も応答せず、ユーザーセッションの`CreateSession`も含まれます。この動作は、コンポジターが終了する場合でも強制終了される場合でも起きるため、終了プロセスはログインから外されます。しかしgreetdの下では、コンポジターはグリーターの端末のフォアグラウンドプロセスグループにあり、greetdのセッションワーカーがその端末を制御します：ワーカーがウォッチドッグ後に終了すると、端末のハングアップによりコンポジターは即座に終了します（マークに`compositor-in-foreground=true`）、そのクローズは依然としてログイン中に実行され、遅延リクエストはコンポジターを見つけません。コンポジターをログイン後も維持するには、独自のセッション内に置く必要があります。ウォッチドッグのPIDは、インスタンスによって指定されたコンポジターの親です。 `hyprland.lock`、および両方ともグリーターユーザーの期待されるプログラムであることが確認されています。また、マークはウォッチドッグが制御プロセスであるかどうか、そしてコンポジタが端末のフォアグラウンドグループにいるかどうかも記録します。制御プロセスが終了するとそのグループはハングアップするためです。ウォッチドッグがない場合、グリーターはコンポジタにただちに終了するよう要求します（`greeter.compositor-exit-requested`）。非アクティブなコンポジタは終了時に出力をそのままにし、カーネルがデバイスを閉じるときに削除するフレームバッファはもはや画面上に表示されません。greetdはユーザーセッションのために自分のVTに切り替えます。切り替えや待機に失敗した場合、グリーターはタイミングログに`greeter.handoff-takeover-failed error=<reason>`を書き込み（ログ自身は実行時ディレクトリにあり、ログアウト時にlogindによって削除されます）、それでもなおコンポジタに終了を要求し、モニターがヘルパーのモードセットで再同期する間、一瞬出力が暗くなります。fbconがあるシステムでは VTにバインドされている場合、コンソールはVT切り替え時に一瞬表示することができます。その前に待つ間、ヘルパーは出力を見つけ、オブザーバーディスクリプタ（`handoff.prepared`）を通して最初のフレームを描画します。どちらもDRMマスターを必要としないため、マスターが空き次第フレームは画面に表示されます。プライマリプレーンにまだフレームがある場合にのみページフリップを試みます。プレーンが空の場合、カーネルはフリップを拒否し、ヘルパーは代わりに同じモードでCRTCを設定します。DRMマスターを待つ間、ヘルパーは各カード上でディスクリプタを開いたままにするため、コンポジタの終了がカーネルにfbdevモードを復元させる最後のクローズになることはなく、タイミングログにすべてのCRTC変更を`handoff.crtc`として記録します（`fb=0`または`mode_valid=false`の行は、二つのマスターの間で出力がオフになったことを意味します）。コネクタは再プローブせずにキャッシュされた状態から読み取り、ページフリップが拒否された場合には`handoff.page-flip-failed errno=<n>`をログに記録します。 そしてそれはモードセットにフォールバックします。`greeter-session`はそのコンポジタ（`ulimit -c 0`）のコアダンプを無効にするので、終了中にクラッシュしてもコアが書き込まれている間にディスプレイがオフのままになることはありません。グリーターコンポジタはXwaylandなしで動作します：KittyとハンドオフサーフェスはWaylandクライアントです。

グリータースプラッシュ、このサーフェス、およびセッションスピナーは、単一のスプラッシュとして読み取られます。グリータースプラッシュとセッションスピナーはWaylandモードでは同じヘルパーです：接続後数ミリ秒で最初のフレームを表示する、プレインな共有メモリレイヤーシェルクライアント（GTKオーバーレイは約300ms必要でしたが、コンポジタはすでに背景を表示していました）、ログイン経路にGTKはありません。3つとも`argvus-loading-theme-core`から同じスピナーを描画します：四角が成長し、次の角に移動し、1.5秒のサイクルで縮小する（CSSローダーキーフレームで、各セグメントに`cubic-bezier(0.3, 1, 0, 1)`）、物理ピクセルで同じサイズ、ユーザーアクセントを色として使用（グリーターは`--accent`を両方のヘルパーに渡します）、フレームは`CLOCK_MONOTONIC`から取得され、1つのプロセスが別のプロセスに引き継いでもアニメーションは再開されません。グリーターコンポジタが出力を同じモードでオンのままにした場合、サーフェスは最初のフレームを表示します モードセットの代わりにページフリップが行われるため、モニターは再同期しません。Hyprlandの最初のモードセットは、まだ描画していないバッファ（黒）をスキャンアウトし、最初のフレームはイベントループが動作してから150〜210ms後に表示されます。したがって、`release`上では、HyprlandがまだDRMマスターを保持している間、サーフェスはそのフレームのコピーをCRTCの空きオーバーレイプレーン（`handoff.overlay plane=<id>`）に配置します。Hyprlandはプライマリおよびカーソルプレーンのみを駆動するため、オーバーレイは最初のフレームの上に残り、オーバーレイバッファ内でスピナーは引き続きアニメーションします（書き込みにはDRMマスターは不要です）。セッションスピナーは`--retire-handoff`と共に動作します：最初のフレームがすべての出力に表示されると、`retire`を送信し、サーフェスはオーバーレイフレームバッファを削除し、そのプレーンだけをオフにします（`handoff.retired`）。Hyprlandがプライマリプレーンを置き換えてから3秒以内に`retire`が届かない場合、サーフェスはオーバーレイを自分で削除します（`handoff.retire-timeout`）、そして10秒後に 交換なしで数秒待つと放棄します（`handoff.replacement-timeout`）。無料のXRGB8888オーバーレイプレーンがない場合（`handoff.overlay-unavailable`）、サーフェスはプライマリバッファのみを保持し、スピナーがアニメーションし続け、Hyprlandがそれを置き換えるまで、その瞬間にHyprlandの描画されていない最初のバッファが表示されます。Hyprlandはアニメーションなしで`argvus-loading-theme`レイヤーをマッピングします（`no_anim`レイヤールール）、そのためスピナーは一フレームで表示され、消えます。マッピングされるまで、Hyprlandはアクティブなテーマのスプラッシュ背景を描画し、それを`argvus config project`が`background_color`として生成された`hypr/state.lua`に書き込みます。

 `argvus-start` は Hyprland を起動する直前に `release` をそのソケット（`/run/argvus-greeter/handoff.sock`）に送信し、ヘルパーは DRM マスターをドロップした後にのみ応答します。グリーターなしのセッションは同じコマンドを送信しますが、サーフェスが見つからないため、何も起こりません。サーフェスの起動失敗はログに記録されますが、ログインは停止しません。起動中は、`/usr/lib/argvus/greeter/handoff --send theme=<name>`、`--send ping`（描画後に応答）、`--send release`、または `--send retire` のコマンドを送ることができます。ソケットはサーフェスが終了するまで開いたままです。ソケットとグリーターの事前ログイン `session.log` は `/run/argvus-greeter` に存在し、`systemd-tmpfiles` が `greeter` ユーザー所有でモード 0755 の状態で作成します：書き込むのはグリーターのみで、ログインするセッションはログを読むだけでソケットに接続します。

視覚的な問題を診断する際には、この分離が重要です：ブートスプラッシュが表示されないのはPlymouth/パッケージの問題であり、空白の遷移はセッションのロードまたはコンポジタの準備の問題であり、認証失敗はデスクトップセッションではなくgreetd/PAMに関連しています。

テーマの切り替えではオーバーレイは表示されません：実行中のデスクトップがその場で変わります。直接セッションをリロードすると、選択されたテーマが明示的に`/usr/lib/argvus/loading-theme/splash`に渡されます。直接リロード（`argvus sessionctl reload`、`SUPER + Shift + R`）では、サーフェスを再作成する場合のみセッションスプラッシュが表示されます：Waybarバーやコントロールパネルの再起動、あるいはフォールバック`full`プランの場合です。プロジェクションはそれなしで動作し、その場でリロードされる変更（Hyprland、テーマ消費者、壁紙、Dunst、polkit、hypridle）は決して表示しません。[argvus-config](/docs/reference/argvus-config/)のリロードターゲットを参照してください。コントロールセンター自体も同じスプラッシュ（`argvus config transition-overlay hold`）を保持し、バーやパネルを再起動する**適用**のため、トリガーされるリロードでは二度目は開始されません。スピナーのみのモードを使用するため、その最初にマッピングされたフレームは不透明であり、`--detached`で開始されます：スプラッシュは短命の`argvus config session-splash start`より長く生存します session-splash start` はそれを起動するヘルパーで、親プロセスの終了シグナルがそのヘルパーの終了と同時にそれを停止させるためです。リロードは、ランタイムの半分が終了した後にスプラッシュを停止し、すべての終了経路で動作します。スプラッシュパレットはあくまでフォールバックです。実行中のセッションでソースの変更が見えない場合は、インストールされているバイナリとパッケージのペイロードを確認してください。

ログインハンドオフソケットは、カーネルのピア資格情報を用いて各クライアントを認証します。制御コマンドを送信できるのは root、ヘルパーの所有者、および greetd によって認証されたアカウントのみです。ソケットがユーザー間の接続を許可していても、他のローカルアカウントは拒否されます。準備された DRM フレームは元のディスクリプタに結び付けられたままです。その非特権ディスクリプタがマスターを取得できない場合、ヘルパーは同じ GPU を再度開き、オブザーバーを開いたままにして、新しいディスクリプタで新しいフレームを準備します。フレームバッファはディスクリプタ間で再利用されることはありません。

## ハンドオフの失敗とキャンセル

グリーターは、引き継ぎが成功するまでDRMヘルパーを所有します。起動失敗、セッションIPCエラー、および引き継ぎ失敗は、その子プロセスを停止および回収し、そのソケットを削除します（`greeter.handoff-cancelled`）。ユーザーセッションのためにヘルパーを切り離すのは、最初のフレームが確認された場合のみです。引き継ぎのタイムアウトは2秒のままで、失敗したヘルパーをキャンセルすると、`argvus-start`で追加の待機を防ぎます。

ヘルパーは、DRMマスターの取得中および描画後に、認証済みコマンドを提供します。早期の`release`は、取得をキャンセルし、準備済みバッファとオブザーバーディスクリプタを閉じ、その後`released`（`handoff.release-before-master`）に応答します。保留中の`ping`は、最初のフレームの後にのみ確認されます。失敗したプレゼンテーションは、成功せずに閉じられます。保留中のピングは一度に1つだけ保持されます。テーマの更新は、プレゼンテーション前に準備済みの背景に適用されます。取得中にも、ピアクレデンシャルおよび境界付きコマンドの読み取りが適用されます。

取得エラーは ` when the errno changes. ` when the errno changes. handoff.acquisition-failed として記録され、最終的な失敗を示します。通常のエラー終了ではソケットが削除されます。これらのマークは、DRMを待っているヘルパーと、実際にフレームを提示したヘルパーを区別します。

この取得は [Linux DRM マスター権限ルール](https://github.com/torvalds/linux/blob/v6.18/drivers/gpu/drm/drm_auth.c)] に従います：かつてマスターになったことがない特権のないディスクリプタは `SET_MASTER` で自身を昇格させることはできませんが、現在マスターのいないプライマリノードを開くことで暗黙的にマスターを取得します。再オープンはグリーターに権限を追加することを回避します。
