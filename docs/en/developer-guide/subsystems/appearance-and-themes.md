---
title: Appearance and themes
description: Theme state propagation across ARGVUS.
---

`argvus-appearance` owns theme, accent, wallpaper and font *state*. It consumes assets from `argvus-wallpapers`, `argvus-fonts` and `argvus-icons`, but it does not generate theme output: every ARGVUS-owned consumer file for Hyprland, GTK, Qt, Waybar, Quickshell, Dunst, Hyprlock, Yazi, Superfile, terminals and native applications is a projection written by `argvus-config` alone, except Rofi: `argvus-launcher` owns its files, and `argvus-appearance` edits the user copies under `data/rofi/`.

The Control Center and Control Panel are user interfaces; neither is the sole source of theme state.

`argvus theme-switch` (also `argvus theme apply`) runs the theme transaction, `argvus config theme-apply`. Under its lock it renders the build of the theme first (a theme that is not installed or does not render changes nothing), commits the selected theme, layout variant and wallpaper through `argvus-config`, points `current` at the build (back at the previous one when the commit fails), writes `.active-theme`, and at once reloads the consumers that read the build directly (`reload_stage = "build"` in the registry: the two Waybar bars, the Control Panel and Hyprland's colours) and shows the theme's wallpaper through hyprpaper. It then copies from the build the files that applications read from their own places (`theme_files::write_build_copies`: kitty, Dunst, Hyprtoolkit, btop, Yazi, Superfile, the removable-devices panel, the calendar and the lock screen), runs the projection (`argvus config project`, which only writes files) and reloads the other consumers (Dunst, btop and kitty). No overlay covers the screen and no service stops: the bars, the panel, Dunst and hyprpaper keep running, and only the colours change. A surface whose consumer is not registered is restarted instead, and Hyprland reloads its configuration when its own consumer is missing. Hyprland reloads its configuration only when the Sticky/Float layout, the theme's effects (`state/effects/<theme>.conf`) or the projected `hypr/state.lua` changed beyond the splash colour and the accent; a layout change also restarts the two Waybar bars, whose margins are layer-shell settings. Sticky and Float are represented canonically by `layout.variant`; the `-float` suffix remains a compatibility fallback. `layout-mode-switch.sh` (`SUPER + Shift + M` and the Control Center) writes `layout.variant` with `argvus config apply-mode` and runs this same transaction for the active family, without a splash and without reloading `argvus-config.service`. The transaction reapplies Hyprland gaps and border geometry with `hyprctl eval`.

The theme transaction of `argvus-config` (`argvus theme-switch`) owns every consumer that cannot read `config.json` or the published projection on its own — the native Qt6ct file, GTK `settings.ini` and `gsettings` hints, Foot and Kitty, the greeter theme state, the taskbar calendar cache, the System Monitor, the wallpaper runtime and Hyprtoolkit. It runs from `argvus sessionctl reload`, so a theme switch, a keybind reload and a session start all reach the same runtime state. Adapters only read the committed generation: they write their own consumer files and caches and never the canonical document or `data/generated/`. The lock screen blurred wallpaper is only invalidated, never rewritten, because it is already part of the committed projection. `argvus config accent` records the canonical accent, renders the build again and reloads every registered consumer in place, so an accent change and a theme change cannot disagree about a variant. The legacy taskbar utility-group marker is imported inside the transaction, and `argvus config taskbar status` reports the effective value without writing a generation.

The Hyprland `SUPER + Shift + T` binding opens `theme-menu.sh`, which selects a theme before invoking that script. While a switch runs, it keeps `theme-switch.active` in the cache directory, with its pid and process start time. The projection that the switch starts reads that marker and leaves the theme to the switch, so the lock is never taken twice. The wait for the lock and for the projection is limited to 60 seconds each, and the reload commands of the consumers to 5 seconds together. A direct `argvus sessionctl reload` (including `SUPER + Shift + R`) applies the already committed generation without projecting again, and it also repairs stale runtime consumers when the canonical value is unchanged. `argvus terminal --apply` generates derived Kitty profiles under the user's cache with a shared lock and atomic replacement.

## Theme builds (`argvus-theme-core`)

`argvus-theme-core` renders themes from data, and the transaction above applies them through a build of the active theme:

- **Build of the active theme.** `argvus theme-switch` renders the active theme (layout and highlight colour included) and points `generated/theme/current` at the build. `argvus config accent` renders it again with the new colour and rewrites the files copied from it, at session start too. The build is required: every themed file comes from it, and an applied Control Center profile keeps it.
- **Consumers read the build.** Each consumer takes its file from `current`: the Waybar taskbar and telemetry `@import` the build stylesheets; rofi's `theme.rasi` imports the build palette; qt6ct's `color_scheme_path` points at it; Hyprtoolkit, application style, Yazi, Superfile, the calendar cache and the removable-devices stylesheet are copied from it; `hyprland.lua`, the Control Panel `Theme.qml`, the lock screen and Dunst read it; kitty includes it and `argvus system-monitor` builds btop's theme from it; the TUI palette uses it for the user's own active theme. A reader without a build of its theme renders it in memory from the manifest: the greeter (official themes only, because it cannot read the user's home), `argvus terminal` and `argvus system-monitor` for another theme, and a session before its first switch. Without a build, `hyprland.lua` uses the ARGVUS Dark colours and the Control Panel its built-in defaults. The per-theme copies of older switches (`data/<app>/themes/`) are moved once to `data/backups/theme-copies-<seconds>/` (`theme_migration`).
- **Reloading.** Each registry entry declares how its running consumer reloads (`rewrite`, `signal` or `command`; a command may use `${ARGVUS_DATA_HOME}` and `${ARGVUS_CONFIG_HOME}`) and when (`reload_stage`). The bars rewrite the first line of their stylesheet (`/* argvus theme build: <build> */`), which their `reload_style_on_change` turns into a style reload without recreating the bar; the Control Panel is called with `qs -c argvus-control-panel ipc call theme reload`; Hyprland evaluates the colours of the active `theme.lua` (`argvus config theme-runtime hyprland`, with the user's accent on the active borders); Dunst runs `dunstctl reload`; btop gets SIGUSR2 and kitty SIGUSR1. `argvus config theme-runtime consumers` runs every reload by hand. The Control Center re-reads its palette when the build or the active theme changes.

- **Theme manifest.** A theme is `themes/<id>/theme.toml` with `schema = 2`: `id`, `name`, `category` (`dark` or `light`), optional `wallpaper` and `preview` (relative to the theme directory or absolute), `[name_i18n]`, `[palette]`, optional `[ansi]` (`color0` to `color15`), optional `[gtk] scheme` and optional `[overrides]`. Official themes live under `/usr/share/argvus/themes/`, user themes under `$XDG_DATA_HOME/argvus/themes/`; an official theme wins over a user theme with the same id, and the directory name must equal the id.
- **Palette.** `bg`, `fg` and `accent` are required; any other lowercase name may be added. An entry is a colour (`#RGB`, `#RRGGBB`, `#RRGGBBAA`) or an expression over other entries, such as `"@accent | alpha(0.13)"`. A highlight colour chosen by the user replaces `accent`, so the entries derived from it follow. Cycles and unknown names are errors.
- **Templates.** Text files where `{{ expression }}` is replaced and `\{{` writes a literal `{{`. An expression reads `palette.<name>` (or `@<name>`), `ansi.colorN`, `layout.<name>` and `theme.id`, `theme.name`, `theme.category`, `theme.variant`, `theme.gtk_scheme`, `theme.wallpaper`, followed by filters: `hex`, `hexa`, `argb` (`#AARRGGBB`), `bare`, `rgb`, `rgba`, `rgba_percent`, `rgb_hex`, `hypr` (`rgba(rrggbbaa)`), `argb_int` (`0xAARRGGBB`), `alpha(x)`, `mix(colour, x)`, `lighten(x)`, `darken(x)`, `contrast`, `upper` and `lower`.
- **Consumer registry.** Each component registers its themed files in `/usr/share/argvus/theme/consumers.d/<id>.toml`: `template` (relative to `/usr/share/argvus`), `output` (relative to the build) and `[reload]` with `kind` `none`, `rewrite` (`path`), `signal` (`process`, `signal`) or `command` (`argv`). `reload_stage = "build"` reloads the consumer as soon as the build is active; the default, `files`, waits until the switch has written the files it reads. A theme can replace one template through `[overrides]`. `[palette]` gives a default to the tokens the template reads, as palette expressions (`btop_cpu_mid = "@fg | mix(@bg, 0.3)"`); a theme that defines the token wins, and two consumers may default the same token only to the same expression. With these defaults a theme needs only `bg`, `fg` and `accent`.
- **Layouts.** `/usr/share/argvus/theme/layouts/{sticky,float}.toml` hold the geometry values templates read as `layout.<name>`, so themes no longer need a `-float` copy.
- **Builds.** A build is rendered in memory, written to `~/.config/argvus/data/generated/theme/builds/<id>-<variant>-<hash>/` through a temporary directory and a rename, and described by its `build.toml` (theme, variant, category, GTK scheme, effective accent, background colour, wallpaper and consumers). A build with the same content is reused. The active build is the target of the `current` symlink beside `builds/`, replaced with one `rename(2)`. Old builds are removed except the active one and the most recent others.
- **Official data.** Every official theme package, and `argvus-appearance` for ARGVUS Dark and Light, ships only `/usr/share/argvus/themes/<id>/theme.toml` (with `overrides/` when needed) and its wallpaper; the per-application copies of the old format are gone. Each component ships its templates under `/usr/share/argvus/<component>/theme-template/` and one registry entry per file in `/usr/share/argvus/theme/consumers.d/` (19 consumers: control panel, taskbar and its menu icon, telemetry, TUI, calendar, launcher, notifications, Hyprtoolkit, application style, Hyprland, Qt6ct, lock screen, terminal, system monitor, Superfile, Yazi flavor and syntax theme, removable devices). `argvus-appearance` ships the Sticky and Float layouts. The palettes and templates were extracted from the old per-theme files and checked for identical output; the manifests keep only the entries that differ from the registry defaults, and a theme whose file has its own structure keeps it as an override. `argvus-appearance/tools/test-theme-switch.py` renders every official theme, and a theme with only the required colours, in both layouts.
- **Template sections.** `{{#if expression}}…{{/if}}` keeps its text only when the value is a non-zero number, non-empty text or a colour; the calendar and TUI stylesheets use it for the rules that exist only in Float. The `contrast` filter gives black or white for text on a colour, `rgba_percent` writes `rgba(r, g, b, NN%)` and `rgb_hex` writes `rgb(rrggbb)`.
- **Commands.** `argvus theme list`, `argvus theme check DIRECTORY` (renders every registered consumer in both layouts and reports every error with its template and line) and `argvus theme render ID` (writes a build, or the files under `--output`, without activating it).
